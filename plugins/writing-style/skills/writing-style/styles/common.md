# 共通コア（全スタイル共通）

このファイルは、casual・formal のどちらでも適用する共通の文章作法。スタイル固有のルールは `casual.md` / `formal.md` を併せて読むこと。

## 文章の流れと論理展開

技術的な正確性を保ちながらも、読みやすく流れのある文章を書く。Martin FowlerやDijkstraの文章から学ぶべきポイント。

### 1. 段落の構成

- **1段落3-5文を基本とする**
  - 1-2文の細切れ段落を避ける
  - 各段落が単一の概念を完結させる
  - 段落間の論理的なつながりを明確にする

❌ 悪い例：

```text
ここで重要な原則を理解する必要がある。それは、分割したものは、いずれ統合して動かす必要があるということだ。

分割は万能薬ではなく、内在するコストが付随する。
```

✅ 良い例：

```text
ここで重要な原則を理解する必要がある。それは、分割したものは、いずれ統合して動かす必要があるということだ。したがって、分割は万能薬ではなく、むしろ内在するコストが付随する。まず、分割されたコンポーネント間の通信や協調といった統合のコストがある。さらに、複数のコンポーネントの監視やデプロイといった管理のコスト、そしてシステム全体を理解するための認知的コストも無視できない。
```

### 2. 箇条書きの適切な使用

- **箇条書きは補助的に使う**
  - 主要な説明は文章で展開する
  - 箇条書きは要点の整理や並列項目の列挙に限定
  - 段落の50%以上が箇条書きにならないようにする

❌ 避けるべき：

```text
分割にはコストが付随する：
- 統合のコスト：分割されたコンポーネント間の通信
- 管理のコスト：複数のコンポーネントの監視
- 理解のコスト：システム全体の把握
```

✅ 推奨：

```text
分割にはコストが付随する。まず、分割されたコンポーネント間の通信や協調といった統合のコストがある。さらに、複数のコンポーネントの監視やデプロイといった管理のコスト、そしてシステム全体を理解するための認知的コストも無視できない。これらのコストを考慮すると、分割は単なる解決策ではなく、トレードオフの選択であることがわかる。
```

### 3. 接続詞による論理の明示

文と文、段落と段落のつながりを明示する：

- **対比・転換**：「しかし」「一方で」「それに対して」「むしろ」
- **因果・結論**：「したがって」「そのため」「結果として」「こうして」
- **補足・説明**：「つまり」「言い換えると」「具体的には」「例えば」
- **追加・強調**：「さらに」「また」「加えて」「実際」

❌ 接続詞なし（論理が不明確）：

```text
マイクロサービスで分けることによって、シンプルにするのが目的だ。従来のモノリシックな巨大アプリケーションを作る場合の技法を、わざわざ小さなサービスに持ち込むのは本末転倒だ。
```

✅ 接続詞あり（論理が明確）：

```text
マイクロサービスで分けることによって、シンプルにするのが目的だ。したがって、従来のモノリシックな巨大アプリケーションを作る場合の技法を、わざわざ小さなサービスに持ち込むのは本末転倒だ。
```

### 4. 文の長さのバリエーション

- **短文と長文を戦略的に配置**
  - 短文：結論や重要なポイントを強調
  - 長文：詳細な説明、複雑な概念の展開
  - 均一な長さの文の連続を避ける

✅ 良い例：

```text
これは問題だ。（短文で断言）
なぜなら、マイクロサービスアーキテクチャを採用する主な目的は、システムをビジネス機能単位で分割し、各サービスを小さくシンプルに保つことで、開発速度と保守性を向上させることにあるからだ。（長文で詳細説明）
```

### 5. 文末表現の多様化

「だ」の連続を避け、文末にバリエーションを持たせる：

- 断定：「〜だ」「〜である」
- 説明：「〜のだ」「〜ということになる」「〜となる」
- 観察：「〜が見られる」「〜と言える」「〜がわかる」
- 推論：「〜だろう」「〜と考えられる」

❌ 単調な繰り返し：

```text
これは問題だ。原因は複雑性の増加だ。結果として保守性が低下するのだ。
```

✅ バリエーション：

```text
これは問題だ。原因は複雑性の増加である。結果として、保守性が低下することになる。
```

### 6. 前の文からの自然な展開

各文が前の文を受けて展開するように書く：

❌ 断絶した展開：

```text
分割したものは統合する必要がある。
分割にはコストがある。
複雑性は移動する。
```

✅ 自然な展開：

```text
分割したものは、いずれ統合して動かす必要がある。したがって、分割は万能薬ではなく、むしろ内在するコストが付随する。このコストの本質は、複雑性が消えるのではなく、形を変えて別の場所に移動することにある。
```

### 7. 断言調と説明調のバランス

一方的な断言を避け、説明的な文章を心がける：

❌ 断言調が過剰：

```text
〜が目的だ。本末転倒だ。ここが本題だ。
```

✅ 説明調を混ぜる：

```text
〜が目的である。このような理由から、本末転倒と言える。ここからが本題となる。
```

### 8. 引用や外部の論説には根拠のURLを付ける

引用は引用元を明確にしてリンクを付ける。リンク先の内容を確認し、確認できない場合は別のリンクを探す、あるいは該当内容は記載しない。リンクの数は、200文字に1つ程度にする。

## 技術内容の記述ルール

### 1. コマンド例の記載方法

```bash
$ コマンド
実行結果をそのまま貼る
```

- プロンプトは `$` で統一
- 実行結果は省略せず、実際の出力をそのまま掲載
- 長い出力でも重要な部分は残す

### 2. 技術用語の扱い

- 英語はそのまま使用（dev container、sparse checkout）
- 必要に応じて日本語訳を併記（「Sparse checkout（疎なチェックアウト）」）
- 略語を積極的に使用（WSL2、VM、VNet）

### 3. コードやファイルへのリンク

- GitHubリポジトリへのリンクを積極的に提供
- 具体的なファイル名と行番号まで示す（`main.json#L20-L104`）
- 「こんな感じのコマンドになる」のような親しみやすい導入

## 読者への配慮

- **実践的なアドバイス**を示す（「手間をかけたくなければ、現状では〜が良い」「グローバル設定は避けてレポジトリ毎に指定した方が良いだろう」）
- **補足説明**は初心者でも分かるように背景を説明する。ただし冗長にならないようポイントを絞る
- **外部リソースへ誘導**する（「困ったら、OAuth2.0 のドキュメントを読むと良い」）

## 禁止事項

避けるべき表現：

- 過度に堅い敬語
- 「です・ます」調の統一（混在OK）
- 技術的な内容だけの無機質な説明

書かないこと：

- 完璧を装う内容（失敗談や試行錯誤を隠さない）
- 他者の成果への批判（基本的に賞賛する姿勢）
- 抽象的すぎる説明（具体例を必ず含める）

## 共通チェックリスト

文章の構成と論理展開：

- [ ] 1段落が3-5文で構成されているか
- [ ] 箇条書きは全体の30%以下に抑えられているか
- [ ] 接続詞で論理的なつながりが明示されているか
- [ ] 短文と長文がバランスよく配置されているか
- [ ] 文末表現に多様性があるか（「だ」の連続を避ける）
- [ ] 各文が前の文から自然に展開しているか
- [ ] 断言調と説明調がバランスよく混在しているか

内容と表現：

- [ ] 実際のコマンド例と実行結果が含まれているか
- [ ] 参考資料への言及があり、URLは内容を確認済みか
- [ ] 実用的な判断・アドバイスが含まれているか
- [ ] 読者との距離感は近いか（堅すぎないか）

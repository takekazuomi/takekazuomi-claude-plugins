# 共通コア（全スタイル共通）

このファイルは、casual・formal のどちらでも適用する共通の文章作法。スタイル固有のルールは `casual.md` / `formal.md` を併せて読むこと。

段落の長さ、箇条書きの比率、文末表現の多様さ、断言と説明の配分は**スタイルごとに方針が異なる**ため、ここでは規定しない。各スタイルのファイルに従う。

## 目次

- **書き始める前に決めること**：読み手・アウトプット・課題・主張を先に定める
- **引用や外部の論説には根拠のURLを付ける**：リンク先の内容を確認する
- **根拠と断定の強さを揃える**：実測値や出典のない断定を避け、穴は `TODO(未確認: ...)` として残す
- **比喩で直截な言明を置き換えない**：mannered prose の除去
- **技術内容の記述ルール**：コマンド例、技術用語、コードへのリンク
- **書式（GFM）**：脚注と注記（alert）の記法
- **禁止事項**
- **共通チェックリスト**：書き終えたあとに全項目を確認する

## 書き始める前に決めること

書き出す前に次の4点を定める。材料が増えるほど焦点が散り、元の課題から離れやすくなるため、この4点が各節を残すかどうかの判断基準になる。

1. **読み手**：誰が読むか、どこまでの前提知識を持つか
2. **アウトプット**：読み終えた読み手が何を得ているべきか。ここから逆算して内容を選ぶ
3. **課題**：この文書が解こうとしている問題は何か
4. **主張**：著者が言いたいことがあるか。あるなら、それは何か

4点は著者が決める。決まっていなければ、書き出す前に著者に確認する。決めた内容を本文に節として書き出す必要はない。

主張のある文章では、主張がもっとも大切である。根拠は主張を支えるために置き、主張が根拠や限定の中に埋もれないようにする。一方、調査レポートやまとめのように、もともと主張の無い文章もある。その場合、主張を作らない。著者が主張を示していないときに、AI が主張を補ってはならない。

## 引用や外部の論説には根拠のURLを付ける

引用は引用元を明確にしてリンクを付ける。リンク先の内容を確認し、確認できない場合は別のリンクを探す、あるいは該当内容は記載しない。リンクの数は、200文字に1つ程度にする。

## 根拠と断定の強さを揃える

原則は1つ。**事実の記述では、断定の強さを手元の根拠の強さと同じにする**。実測値や確認済みの出典があるなら言い切ってよい。無いときは、曖昧に弱めるのではなく、何が未確認なのかを書く。

❌ 根拠なしの断定：

```text
この構成にすればレスポンスは大きく改善する。
```

❌ 弱めただけ（何が不明なのか伝わらない）：

```text
この構成なら改善するかもしれない。
```

✅ 強度を揃える：

```text
この構成で p99 は 420ms から 180ms になった。ただし 10k/s 以上の負荷は未計測。
```

「ただし〜は未計測」は弱い文に見えるが、正確な文である。読者が自分の状況に当てはめて判断できるようになる。

この節が扱うのは事実の記述である。著者の主張は、根拠の強さに合わせて弱めない。主張を支える事実に根拠が無いときは、事実の側に TODO を置き、主張は著者のものとして言い切る。主張そのものに TODO や限定を付けて弱めない。

### 穴を穴として出す

材料が無い箇所を修辞で埋めない。埋め草は決まった形で現れるので、下書きから機械的に探せる（`scripts/lint.sh`）。

<!-- lint-off -->

- 段落末の一行断定（「ここが一番効く」「本質はここにある」「結局〜に尽きる」）
- 種明かし構文（「Xの正体は」「要するにXとは」）
- 対比構文（「〜ではなく、〜だ」）
- メタ説明（「重要なのは〜という点だ」）
- 根拠を伴わない強調語（まさに、非常に、極めて、シームレス、革新的、〜を実現する）
- 測っていない数値（「だいたい2割減る」「3倍速い」）

<!-- lint-on -->

いずれも、書き手の確信ではなく確信の体裁だけを作る。該当箇所は消して滑らかにせず、`TODO(未確認: 10k/s 以上の負荷)` の形で残して著者に返す。

### TODO の置き方

`TODO(未確認: ...)` は casual・formal で同じ形式を使う。著者へ返す下書きの印であり、著者が材料を足して埋めるか、未確認のまま残すと判断する。

全文に TODO を散らすと、判断の放棄に見える。主張の骨格は言い切り、根拠の強度差だけを明示する。

```text
A を選んだ。理由は B。ただし C の条件下では未検証。
```

この形なら主張の強さと根拠の強さが揃っていて、読み物としても弱くならない。残った TODO は、そのまま次の検証タスクになる。

## 比喩で直截な言明を置き換えない

Anthropic は、修辞や比喩が直截な言明を置き換える型を **mannered prose** と呼んでいる（[Prompting Claude Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1)）。「動かす価値のあるパラメータ」と書けるところを「回す価値のあるダイヤル」と書く類がこれにあたる。

害は2つある。ひとつは読者に余計な労力を強いること。もうひとつは精度が落ちることで、比喩は書き手が選んでも制御してもいない含意を連れてくる。直截な語があるなら、そちらを使う。

<!-- lint-off -->

- ❌「この設計は技術的負債の利息を払い続ける」→ ✅「この設計では変更のたびに同じ修正が必要になる」
- ❌「ここが設計の心臓部だ」→ ✅「ここでリクエストの振り分けを決めている」
- ❌「キャッシュが呼吸を始める」→ ✅「ヒット率が安定する」

<!-- lint-on -->

比喩そのものは禁じない。落とすのは**直截な言い換えが存在する箇所に置かれた比喩**に限り、直截な表現では説明できない概念の比喩は残してよい。言い換えが存在するかどうかは機械では判定できないため、迷う箇所は著者に示す。

前節「根拠と断定の強さを揃える」とは別の軸である。前節は根拠と断定の較正を、この節は表現の精度を見る。「だいたい2割減る」は比喩ではないので、この節の観点では落ちない。両方を通す。

## 技術内容の記述ルール

### 1. コマンド例の記載方法

```bash
$ コマンド
実行結果
```

- プロンプトは `$` で統一
- 実行結果を載せる（掲載範囲はスタイル側の規定に従う）

### 2. 技術用語の扱い

- 英語はそのまま使用（dev container、sparse checkout）
- 必要に応じて日本語訳を併記（「Sparse checkout（疎なチェックアウト）」）
- 略語を積極的に使用（WSL2、VM、VNet）

### 3. コードやファイルへのリンク

- GitHubリポジトリへのリンクを積極的に提供
- 具体的なファイル名と行番号まで示す（`main.json#L20-L104`）

## 書式（GFM）

Markdown は GFM（GitHub Flavored Markdown）で書く。

### 脚注

本文に `[^1]` を置き、文書末尾に定義を書く。

```markdown
Kalai ら[^1]は、評価の採点方法が当て推量を促すとしている。

[^1]: Kalai et al., *Why Language Models Hallucinate*, 2025 <https://arxiv.org/abs/2509.04664>
```

- 参照記号は上付きの番号で表示される。文頭や表のセルに単独で置かず、出典名の直後に付ける
- 脚注に何を書くか（説明や評価の有無）は、スタイル側の規定に従う

### 注記（alert）

補足や警告を本文から分けて示すときは、GFM の alert を使う。種類は `NOTE`・`TIP`・`IMPORTANT`・`WARNING`・`CAUTION` の5つ。

```markdown
> [!WARNING]
> この操作は取り消せない。
```

本文で足りる内容を alert にしない。alert が多いと、どれも目立たなくなる。

## 禁止事項

- 抽象的すぎる説明（具体例を必ず含める）
- 根拠を確認していない引用・リンク
- 測っていない数値や未確認の事実を、確認済みの記述と同じ確信度で書くこと
- 根拠のない一行断定で段落を締めること
- em ダッシュ（`—`）や en ダッシュ（`–`）による挿入句。読点・句点・丸括弧で書く
- 著者が示していない主張を作ること

## 共通チェックリスト

書き終えたあとに AI が確認する項目。飛ばすと害が大きく、見落とされやすいものだけを置く。語句や表記のように機械で拾えるものは `scripts/lint.sh` と textlint に任せる。中身の判断が要るもの（関連性、重みづけ、構成、比喩の言い換え、主張が埋もれていないか）は、ここに置かず著者に示す。

- [ ] 書き始める前に、読み手・アウトプット・課題・主張を著者と確認したか
- [ ] 数値・固有名詞・引用を、実測値か確認済みの出典と照合したか。照合できないものは `TODO(未確認: ...)` にしたか
- [ ] 引用・参照のリンク先が開け、引用した内容がそこに書かれているか
- [ ] 著者が示していない主張・体験・評価を書き足していないか（書き始める前に確認した主張と照合する）
- [ ] 著者の主張に、TODO や限定を付けて弱めていないか
- [ ] 表記ゆれ（同じ概念の別表記、固有名のつづりの不統一）がないか
- [ ] `scripts/lint.sh` と textlint を通したか（ERROR は0件にする。WARN は著者に示す）

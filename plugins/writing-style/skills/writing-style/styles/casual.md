# casual スタイル（レポート・ブログ・Zenn記事）

`common.md` に加えて、このファイルのルールを適用する。対象はレポート、ブログ（Blogspot）、Zennの技術記事。砕けた親しみやすいレジスター。

## 目次

- **基本方針**：人間味のある散文。技術的な正確さは保つ
- **文章の構成**：段落の長さ、箇条書きの比率、文の長さ、文末表現
- **文体・表現**：著者の感情・評価、著者の判断・感想、カジュアルな文末
- **記事構成パターン（3部構成）**：導入部・本文・締めくくり
- **参照と脚注**：GFM の脚注、参考記事への説明
- **特徴的な要素**：事実と推論の分離、時間の表現、話題の転換など
- **読者への配慮**：実践的なアドバイス、補足説明、実行結果の掲載
- **禁止事項**
- **casual 固有チェックリスト**：共通チェックリストを使う

## 基本方針

技術的な正確性を保ちながら、**人間味のある親しみやすい文章を散文調で書く**。読者との距離感を近くし、実践的な内容を重視する。

文章の流れは Martin Fowler や Dijkstra の文章に学ぶ。

## 文章の構成

### 1. 段落の構成

- **1段落3-5文を基本とする**
  - 1-2文の細切れ段落を避ける
  - 各段落が単一の概念を完結させる
  - 段落間の論理的なつながりを明確にする

✅ 良い例：

```text
ここで重要な原則を理解する必要がある。それは、分割したものは、いずれ統合して動かす必要があるということだ。したがって、分割は万能薬ではなく、むしろ内在するコストが付随する。まず、分割されたコンポーネント間の通信や協調といった統合のコストがある。さらに、複数のコンポーネントの監視やデプロイといった管理のコスト、そしてシステム全体を理解するための認知的コストも無視できない。
```

### 2. 箇条書きは補助的に使う

- 主要な説明は文章で展開する
- 箇条書きは要点の整理や並列項目の列挙に限定
- 箇条書きは全体の30%以下に抑える

### 3. 文の長さのバリエーション

- **短文と長文を戦略的に配置**
  - 短文：結論や重要なポイントを強調
  - 長文：詳細な説明、複雑な概念の展開
  - 均一な長さの文の連続を避ける

✅ 良い例：

```text
これは問題だ。（短文で断言）
なぜなら、マイクロサービスアーキテクチャを採用する主な目的は、システムをビジネス機能単位で分割し、各サービスを小さくシンプルに保つことで、開発速度と保守性を向上させることにあるからだ。（長文で詳細説明）
```

### 4. 文末表現の多様化

文末の単調な繰り返しを避ける。

## 文体・表現

### 1. 著者の感情・評価を削らない

著者が示した感情や評価（「素晴らしい」「気に入って使ってる」「orz」）は、砕けた言い方のまま残す。整えるつもりで平板にしない。材料の無い箇所に足さない。

著者の材料がある場合の言い方の例：

- ❌「便利だった」→ ✅「なかなか便利だった」
- ❌ `忘れていたが思い出してきた`
- ✅ `だいぶ忘れていたがだいぶ思い出してきてる`

個人的な体験談・感想は、著者のものであれば望ましい。ただし**事実に即さない体験の創作は禁止**。体験を入れられそうな箇所は、レビュー時に著者へ確認する（勝手に作らない）。

人間味のある表現は材料を必要としないため、材料の無い箇所を埋める道具として一番使われやすい。感情表現や体験談は、実際に体験がある箇所にだけ置く。材料の無い箇所は `common.md` の「根拠と断定の強さを揃える」に従い、TODO として残す。

### 2. 著者の判断・感想をぼかさずに書く

著者が示した判断・感想は、ぼかさずに書く。AI が判断や感想を作らない。著者の判断・感想の言い方の例：

- 「個人の嗜好の部分をどこまで入れるのかは微妙な感じではある」
- 「ちょっと混乱するが、まあ納得できる範囲かな」
- 「贅沢を言うと、VS Code だけでなく、他のエディターでも使えると嬉しいところではある」
- 「手間をかけたくなければ」のような実用的な判断を示す

### 3. カジュアルな文末表現

- 「〜している」→「〜してる」
- 「〜だったので」
- 「〜してしまう」「〜してしまうことがある」
- 「〜ってわけです、簡単ですね」

## 記事構成パターン（3部構成）

### 導入部

1. きっかけ・動機（最近〜することが多く）
2. 問題意識（〜が気になることがママある）
3. 解決策・やったこと（〜を作成した／試してみた）

### 本文

1. 概要説明
2. 実際のコマンド例（`$` プロンプト付き）
3. 実行結果（省略せずに掲載）
4. 結果の確認
5. ポイントの解説

### 締めくくり

1. 「最後に」または「まとめ」セクション
2. 実用的な判断（「今でも十分便利に使える」「筋が良いので積極的に使った方が良い」）
3. 注意点の追記（「ただし、〜は要注意」）

## 参照と脚注

- GFM の脚注を使う（`common.md` の「書式（GFM）」）。本文 `[^1]`、末尾 `[^1]: 説明文 URL`
- 記事末尾に参照セクションを設ける
- 参考記事には内容の説明を1〜2行つける。評価（「素晴らしい」「必見の情報満載」「お勧めですよ」）は、著者が読んで評価したものに限る。AI は評価を作らず、内容の説明だけを書く。コミュニティでの評価があれば、出典を付けて書いてよい
- **本文＝主張、脚注＝検算用の足場**。結論を最短で届けたい読者には本文を、自分で検算したい読者には脚注を渡す設計にする。ただし、主張の強さを左右する反証は脚注ではなく本文に短く残す

## 特徴的な要素

- **事実と推論の分離**：事実、推論、独自の決定を明確に分ける。事実は根拠のURLを付ける
- **時間の表現**：「先日(7/30)と言っても、既に2ヶ月前」のような曖昧で人間的な表現を使う
- **話題の転換**：「話がズレた」「閑話休題」で本題に戻る。著者の経験があるときは、個人的な経験談を挟む（「このBlog、2年ほど空いてしまったが」）
- **画像の配置**：記事の雰囲気を和らげる写真（風景など）を挿入する
- **エラーや問題への言及**：エラーメッセージはそのまま引用する。`なかなか難儀する`、`昔は使ってたんだけど、、、orz` のような苦労話を隠さない
- **著者の比喩**：著者が使った比喩（開発環境の複雑化を「魔窟化」と呼ぶなど）は、著者の言い回しとして残す。AI は比喩を作らず、著者の比喩も書き換えない。直截な言い換えがありそうな箇所は、候補として著者に示すだけにする（`SKILL.md` の工程9）

## 読者への配慮

- **実践的なアドバイス**を示す（「手間をかけたくなければ、現状では〜が良い」「グローバル設定は避けてレポジトリ毎に指定した方が良いだろう」）
- **補足説明**は初心者でも分かるように背景を説明する。ただし冗長にならないようポイントを絞る
- **外部リソースへ誘導**する（「困ったら、OAuth2.0 のドキュメントを読むと良い」）
- **実行結果は省略せず**、実際の出力をそのまま掲載する。長い出力でも重要な部分は残す

## 禁止事項

避けるべき表現：

- 過度に堅い敬語
- 「です・ます」調の統一（混在OK）
- 技術的な内容だけの無機質な説明

書かないこと：

- 完璧を装う内容（失敗談や試行錯誤を隠さない）
- 他者の成果への批判
- AI が作った、他者の成果への感想。コミュニティでの評価があれば、出典を付けて書いてよい

## casual 固有チェックリスト

`common.md` の共通チェックリストを使う。casual に固有の確認項目は置かない。

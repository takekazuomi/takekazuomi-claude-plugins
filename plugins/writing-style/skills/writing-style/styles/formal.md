# formal スタイル（技術文書）

`common.md` に加えて、このファイルのルールを適用する。対象は Issue、PR の説明、Design Doc、仕様書、設計書、議事録。

## 基本方針

正確さ・簡潔さ・検証可能性を最優先する。読み手が誤解なく意図を取れることが唯一の目的であり、**冗長さは文体の好みではなく欠陥として扱う**。

casual と異なり、人間味・体験談・感情表現は求めない。ただし無機質な箇条書きの羅列も避け、判断の理由が後から再構成できる文章にする。

判断の基準は「読み手のレベルによらず、得られるアウトプットが一定に伝わるか」に置く。

## 1. 書き始める前に決めること

書き出す前に次の3点を定める。ここが定まれば文書の半分は完成している。

1. **読み手** — 誰が読むか、どこまでの前提知識を持つか。前提がそろっていない読み手がいるなら、導入で水準をそろえる
2. **アウトプット** — 読み終えた読み手が何を得ているべきか（決裁、実装方針の理解、合意事項の確認）。ここから逆算して内容を選ぶ
3. **課題** — この文書が解こうとしている問題は何か。「なぜそれが重要か」を問い、正しい問いになっているかを確かめる

自分が持っている技術や作ったものから書き始めない（skills-forward の回避）。課題が先、手段は後である。

## 2. 文書種別と骨子

文書種別ごとに次の骨子を基本とする。すべてを機械的に並べる必要はなく、不要な節は省く。**事実が確認できないものは書かない**。

| 文書種別 | 骨子 |
| --- | --- |
| Design Doc・仕様書・設計書 | 概要（何の文書か、1-2段落）／目的（解こうとしている問題）／背景・動機／Goals・Non-Goals／本論（設計・方式・手順）／決定事項と根拠／未決事項（Open Questions）／関連ドキュメント |
| Issue | 解きたい問題／背景・現状／期待する結果／受け入れ条件／関連リンク |
| PR の説明 | 目的と紐づく Issue／変更点／設計判断と根拠／検証方法と結果／影響範囲と非対象 |
| 議事録 | 日時・参加者／議題／決定事項と根拠／未決事項と担当・期限 |

結論を先に置く。背景から書き起こして結論に至る、いわゆる起承転結の構成は取らない。

長さは本体を15〜20分で読み切れる分量に収める。詳細なログ、全項目の一覧、補足の検証結果は Appendix に逃がし、本体には判断に必要なものだけを残す。

### frontmatter と日付

Design Doc・仕様書は冒頭に YAML frontmatter を置き、`title`・`date`・`version` を必須とする。日付は ISO 形式（`2026-09-08`）の絶対日付で書く。

「最近」「先日」「いつのまにか」のような曖昧な相対時間は使わない。相対表現が必要な場合も、初出で絶対日付を併記する。

相対表現で書いた記述は、読む時期によって意味が変わる。ロードマップや移行計画のように、いつ時点の事実かが判断を左右する文書では誤読の原因になる。

### 決定・根拠・未決事項を残す

設計判断は結論だけでなく根拠を残す。複数案を比較したときは、採用案の理由と、却下した代替案とその理由も記録する。後から読む人が判断を再構成できるようにする。

選択肢は MECE（漏れなく重複なく）に並べ、**必ず推奨案を示す**。選択肢を並べただけで結論を書かない文書は、読み手に判断を丸投げしている。

判断が後戻りできるかどうかを明記する。取り消せない決定（one-way door）は慎重に根拠を積み、取り消せる決定（two-way door）は速く決めてよい。この区別を書き残すと、後続の議論の熱量が適正になる。

確定していない論点は「要確認」「未定」として明示し、断定と区別する。この明示は曖昧さを残すことではない。何が決まっていないかを読み手に正確に伝えるために書く。

## 3. 文体

### 常体を基本とする

- 常体（である調）を基本とする
- 過度に堅い敬語を避ける
- 「です・ます」調と混在させない（節内では必ずそろえる）
- カジュアルな文末（「〜してる」「〜しちゃう」）は使わない

ただし議事録で他者の発言を引用する場合は、原文の文体をそのまま残す。引用を改変しないことを優先する。

### 1文1アイデア

一文に複数の概念を詰め込まない。「または」「かつ」で分岐する長文や、文中に埋め込まれたリストは、文を分けるか箇条書きへ変換する。

`which`・`that` にあたる修飾節が主題を延長せず別の主題へ分岐する場合は、文を分割する。

一文が150字を超えると読み解けなくなる。この上限は `scripts/textlint.sh formal` が機械的に検査する。

### 能動態で書く

行為や判断の主体が自分たちであれば能動態で書く。主語を省略して受け身にすると、主体が文から完全に消える。誰が決めたのかを後から復元できなくなり、「判断を再構成できるようにする」という方針に反する。

焦点が対象物や状態にあり、行為者が背景に退いてよい場合は受け身でよい。自動生成のように行為者が仕組みである場合も同様とする。

❌ 主体が消える：

```text
残る案が妥当と判断された。
置き場所の候補は3つ検討された。
```

✅ 主体を明示する：

```text
残る案が妥当と判断した。
置き場所の候補は3つ検討した。
```

✅ 焦点が対象物にあり、受け身でよい：

```text
検証に使う関数はすでに用意されている。
プロキシサービスのフォルダは自動生成される。
```

### 段落は1アイデア

各段落が単一のアイデアを完結させる。判断の基準は文数ではなく、その段落で扱うアイデアが1つかどうかに置く。[Google developer documentation style guide](https://developers.google.com/style/paragraph-structure) は1段落1アイデアを定め、文数の下限を置いていない。1文だけの段落も認める。

5-6文を超えたら、情報を詰め込みすぎているサインと考える。ただし単一のアイデアを扱っている限りは6文を超えてもよい。[Google Technical Writing One](https://developers.google.com/tech-writing/one/paragraphs) は読み手が受け入れやすい長さを3-5文とし、7文を超える段落は避けられるとしている。

これは目安であって下限ではない。段落を長くするためだけに説明を追加しない。

### 曖昧さを排除する

指示語（これ・それ・あれ）の指す対象を明確にする。主語を省略しすぎず、誰が・何がの主体をはっきりさせる。一文に複数の解釈が生じる構文を避ける。

### 具体的な数値で書く

程度を表す形容詞は、読み手ごとに解釈が変わる。効果・規模・条件は数値で書く。

❌ 解釈が読み手に委ねられる：

```text
この変更でレスポンスが大幅に速くなった。対象データもかなり多い。
```

✅ 数値で示す：

```text
この変更で p99 レイテンシが 100ms から 10ms に下がった。対象データは約 240 万件である。
```

### 用語の一貫性

主要な用語は初出時に定義する。略語や独自用語が多い文書では、冒頭に用語表を置く。

同じ概念を別の語で言い換えない（表記ゆれを避ける）。製品名・固有名のつづりと大文字小文字を統一する。矢印などの記号も文書内で統一する。

## 4. 冗長さの排除

書き終えたら、次の語句を機械的に置換または削除する。

| 冗長な表現 | 置換 |
| --- | --- |
| 〜することが可能である | 〜できる |
| 〜を行う／〜を実施する | 動詞化（「検証を行う」→「検証する」） |
| 〜という点において | 〜で |
| 〜に関して／〜について言えば | 〜は |
| 現時点においては | 現在／（多くは削除可能） |
| 〜のような形になっている | 〜である |

次の語は主張を弱めるだけで情報を持たない。削除する。

- 基本的に、一般的に、原則として（例外を実際に述べない場合）
- なお、ちなみに、ある意味
- 非常に、かなり、しっかりと

装飾目的のヘッジも使わない。「〜と言える」「〜ということになる」「〜と考えられる」は、実際に推論であることを示す場合にだけ使う。断定できることは断定する。

❌ 装飾のヘッジ：

```text
この方式は移行コストが低いと言える。したがって採用が妥当ということになる。
```

✅ 断定と推論を区別する：

```text
この方式は移行コストが低い。したがって案Aを採用する。ただし本番相当の負荷での挙動は未検証であり、性能要件を満たすかは確認が必要である。
```

## 5. 箇条書き（役割分担ルール）

箇条書きは項目間の関係（因果・順序・条件・トレードオフ）を表現できない。そのため**論証を箇条書きで代替すると論理が失われる**。一方、走査・追跡が目的の情報では箇条書きが散文より優れる。したがって禁止も多用もせず、役割で分ける。

- 散文が担うもの：なぜ・文脈・因果・トレードオフ・判断の根拠
- 箇条書きが担うもの：走査・追跡・参照する原子（手順、チェック項目、選択肢の列挙、成果物、関連リンク）

比率の数値上限は課さない。Issue や PR はリスト主体になって構わない。禁じるのは、複数案の比較や採否の根拠といった**論証を箇条書きだけで済ませること**である。

### 散文とリストを重複させない

散文とリストの併用は、役割を分ければ冗長にならない。冗長になるのは、両者が同じ内容を二重に述べるときだけである。

リード文で項目を全部言い換えない。共有の文脈（なぜ・前提）を一度だけ与え、各項目の中身はリスト側に持たせる。

❌ 重複（散文とリストが同じ内容）：

```text
確認すべき論点は2つある。ひとつは削除連携の可否で、検査と診療課題も必要か確認する。もうひとつは表示制御で、切替を抑制できるか確認する。

- [ ] 削除連携の可否
- [ ] 表示制御
```

✅ 役割分担（リード＝文脈、リスト＝追跡項目）：

```text
確認すべき論点が2つ残っている。いずれも案A（複製方式）を前提とした運用面の確認である。

- [ ] 検査・診療課題の削除連携は可能か（処方は可能）
- [ ] 対象サービスを WebView 側に表示させない（切替抑制）ことは可能か
```

### 箇条書きの書式

- 順序に意味がある手順は番号付きリスト、意味がないものは箇条書きにする
- 番号付きの手順は命令形の動詞で始める（「設定ファイルを作成する」）
- 同一リスト内で構文をそろえる（並列構造）
- 行末に句読点を付けない。体言止めまたは句点なしで終える。地の文（段落）には通常どおり句点を使う
- 1項目だけのリストを作らない。リストになっていない

❌ 行末に句点：

```text
- 統合のコストは、分割されたコンポーネント間の通信である。
- 管理のコストは、複数のコンポーネントの監視である。
```

✅ 行末に句点なし：

```text
- 統合のコスト：分割されたコンポーネント間の通信
- 管理のコスト：複数のコンポーネントの監視
```

## 6. 正確性と検証可能性

### 真実の源にリンクする

主張は検証可能にする。仕様書・Issue・PR・外部ドキュメントなど、真実の源（source of truth）へリンクを張る。

引用は引用元を明確にし、リンク先の内容を確認する。確認できない場合は、別のリンクを探すか、該当内容を記載しない。リンクの数は200文字に1つ程度を目安とする。

参照は `[[1]](#ref1)` 形式で記載し、文書末尾に参照セクションを設ける。参考資料への主観的な評価（「素晴らしい」「お勧め」）は書かない。

### 未確認情報を明示する

確定した事実と、未確認・推測を区別する。未確認の内容は「要確認」「未定」で明示し、断定と混ぜない。古くなった可能性がある記述には、いつ時点の情報かを添える。

## 7. 図・表・コード

### 図版

構造や流れは図で示す。図にはキャプションを付け、本文から「下図」「次の図」などで参照して位置づけを与える。

ただし図は補助である。図を見なければ意味が通らない文書にしない。主要な内容は自然言語で伝わるようにし、図はその理解を速めるために置く。

### 表

並列する選択肢の比較や、属性の一覧には表を使う。観点（列）をそろえ、各案を同じ軸で比較できるようにする。

### コード・コマンド例

必要なときだけ載せる。プロンプトは `$` で統一する。出力を貼る場合は要点を残し、冗長な部分は省く。コードやファイルを参照するときは、具体的なファイル名と行番号まで示す（`main.json#L20-L104`）。

## 8. 鮮度・改訂管理

frontmatter の `date`・`version` を更新の起点とする。古くなった記述は、削除するか、いつ時点のものかを明示する。廃止した方針は deprecated として残し、なぜ廃止したかがわかるようにする。

## 禁止事項

- 曖昧な相対時間（「最近」「先日」「いつのまにか」）。絶対日付で書く
- 根拠のない断定、未確認情報の事実としての記載
- 論証（複数案の比較、採否の根拠、因果の説明）を箇条書きだけで済ませること
- 選択肢だけを並べて推奨案を書かないこと
- 課題ではなく手持ちの技術から書き起こすこと（skills-forward）
- 行為や判断の主体が自分たちであるのに受け身で書くこと
- 表記ゆれ（同義語の混在、固有名のつづり不統一）
- 抽象的すぎる説明（具体例・図・数値で裏づける）
- カジュアルな文末、感情表現、体験談、参考資料への主観的評価
- 段落を伸ばすためだけの言い換えと、装飾目的のヘッジ

## formal 固有チェックリスト

構造と正確性：

- [ ] 読み手・アウトプット・課題が定まっているか。読み手が「だから何？」と感じないか
- [ ] 文書種別に応じた骨子がそろっているか
- [ ] 結論が先に置かれているか
- [ ] 本体が15〜20分で読み切れる分量か。詳細は Appendix に逃がしたか
- [ ] 選択肢が MECE に並び、推奨案が明示されているか
- [ ] 後戻りできる決定か（one-way / two-way door）が示されているか
- [ ] 効果・規模・条件が数値で書かれているか（「速い」「多い」で済ませていないか）
- [ ] frontmatter に `title`・`date`・`version` があり、日付が絶対日付か（Design Doc・仕様書）
- [ ] 採用案の根拠と、却下した代替案が記録されているか
- [ ] 未決事項が「要確認」「未定」で断定と区別して明示されているか
- [ ] 主張に真実の源（仕様・Issue・PR・外部資料）へのリンクがあるか
- [ ] リンク先の内容を確認したか
- [ ] 用語が初出で定義され、表記ゆれがないか

文体と簡潔さ：

- [ ] 常体でそろっているか。カジュアルな文末が混じっていないか
- [ ] 一文が単一のアイデアに絞られているか
- [ ] 行為や判断の主体が受け身で消えていないか
- [ ] 段落が単一のアイデアに絞られ、5-6文を超えていないか。水増しの言い換えがないか
- [ ] 冗長表現の置換表と空語の削除を適用したか
- [ ] 装飾目的のヘッジを使っていないか
- [ ] 指示語の指す対象が明確か

箇条書きと図表：

- [ ] 論証を箇条書きだけで済ませていないか
- [ ] リード文とリストが同じ内容を重複していないか
- [ ] 箇条書きの行末に句読点が付いていないか
- [ ] リスト内の構文がそろっているか
- [ ] 比較が観点のそろった表で示されているか
- [ ] 図にキャプションがあり、本文から参照されているか。図なしでも意味が通るか

仕上げ：

- [ ] typo、壊れたリンク、コピペの残骸がないか
- [ ] 見出しの階層・記号・表記が文書内でそろっているか
- [ ] `scripts/textlint.sh formal` で機械検査したか（表記・語法のみ。論理と構成はこのリストで見る）

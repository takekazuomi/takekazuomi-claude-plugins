# formal スタイル（技術文書）

`common.md` に加えて、このファイルのルールを適用する。対象は Issue、PR の説明、Design Doc、仕様書、設計書、議事録。

## 目次

- **基本方針**：正確さ・簡潔さ・検証可能性を優先する
- **1. 書き始める前に決めること**：読み手・アウトプット・課題の詰め方、skills-forward の回避
- **2. 文書種別と骨子**：種別ごとの骨子、結論先出し、日付
- **3. 文体**：常体、1文1アイデア、能動態、段落
- **4. 冗長さの排除**：冗長な表現の置換表、空語、装飾のヘッジ
- **5. 箇条書き（役割分担ルール）**：散文とリストの役割、重複の回避、書式
- **6. 正確性と検証可能性**：真実の源へのリンク、未確認情報の明示
- **7. コード・コマンド例**
- **formal 固有チェックリスト**：書き終えたあとに全項目を確認する

## 基本方針

正確さ・簡潔さ・検証可能性を最優先する。読み手が誤解なく意図を取れることが唯一の目的であり、**冗長さは文体の好みではなく欠陥として扱う**。

casual と異なり、人間味・体験談・感情表現は求めない。ただし無機質な箇条書きの羅列も避け、判断の理由が後から再構成できる文章にする。

判断の基準は「読み手のレベルによらず、得られるアウトプットが一定に伝わるか」に置く。

## 1. 書き始める前に決めること

`common.md` の「書き始める前に決めること」（読み手・アウトプット・課題・主張）を定める。ここが定まれば文書の半分は完成している。formal では、読み手・アウトプット・課題を次の観点で詰める。

1. **読み手**：前提がそろっていない読み手がいるなら、導入で水準をそろえる
2. **アウトプット**：決裁、実装方針の理解、合意事項の確認のどれかを明確にする
3. **課題**：「なぜそれが重要か」を問い、正しい問いになっているかを確かめる

自分が持っている技術や作ったものから書き始めない（skills-forward の回避）。課題が先、手段は後である。

## 2. 文書種別と骨子

文書種別ごとに次の骨子を基本とする。すべてを機械的に並べる必要はなく、不要な節は省く。**事実が確認できないものは書かない**。

| 文書種別 | 骨子 |
| --- | --- |
| Design Doc・仕様書・設計書 | 概要（何の文書か、1-2段落）／目的（解こうとしている問題）／背景・動機／Goals・Non-Goals／本論（設計・方式・手順）／決定事項と根拠／未決事項（Open Questions）／関連ドキュメント |
| Issue | 解きたい問題／背景・現状／期待する結果／受け入れ条件／関連リンク |
| PR の説明 | 目的と紐づく Issue／変更点／設計判断と根拠／検証方法と結果／影響範囲と非対象 |
| 議事録 | 日時・参加者／議題／決定事項と根拠／未決事項と担当・期限 |

結論を先に置く。背景から書き起こして結論に至る、いわゆる起承転結の構成は取らない。

### 日付

日付は ISO 形式（`2026-09-08`）の絶対日付で書く。

「最近」「先日」「いつのまにか」のような曖昧な相対時間は使わない。相対表現が必要な場合も、初出で絶対日付を併記する。

相対表現で書いた記述は、読む時期によって意味が変わる。ロードマップや移行計画のように、いつ時点の事実かが判断を左右する文書では誤読の原因になる。

## 3. 文体

### 常体を基本とする

- 常体（である調）を基本とする
- 過度に堅い敬語を避ける
- 「です・ます」調と混在させない（節内では必ずそろえる）
- カジュアルな文末（「〜してる」「〜しちゃう」）は使わない

ただし議事録で他者の発言を引用する場合は、原文の文体をそのまま残す。引用を改変しないことを優先する。

### 1文1アイデア

一文に複数の概念を詰め込まない。分岐する長文や文中に埋め込まれたリストは、文を分けるか箇条書きにする。150字の上限は `scripts/textlint.sh formal` が検査する。

### 能動態で書く

行為や判断の主体が自分たちであれば能動態で書く。受け身で主語を省くと、誰が決めたのかを後から復元できなくなる。焦点が対象物や状態にある場合や、行為者が仕組みである場合（自動生成など）は受け身でよい。

### 段落は1アイデア

各段落が単一のアイデアを完結させる。判断の基準は文数ではなく、その段落で扱うアイデアが1つかどうかに置く。[Google developer documentation style guide](https://developers.google.com/style/paragraph-structure) は1段落1アイデアを定め、文数の下限を置いていない。1文だけの段落も認める。

5-6文を超えたら、情報を詰め込みすぎているサインと考える。ただし単一のアイデアを扱っている限りは6文を超えてもよい。[Google Technical Writing One](https://developers.google.com/tech-writing/one/paragraphs) は読み手が受け入れやすい長さを3-5文とし、7文を超える段落は避けられるとしている。

これは目安であって下限ではない。段落を長くするためだけに説明を追加しない。

## 4. 冗長さの排除

書き終えたら、次の語句を機械的に置換または削除する。

<!-- lint-off -->

| 冗長な表現 | 置換 |
| --- | --- |
| 〜することが可能である | 〜できる |
| 〜を行う／〜を実施する | 動詞化（「検証を行う」→「検証する」） |
| 〜という点において | 〜で |
| 〜に関して／〜について言えば | 〜は |
| 現時点においては | 現在／（多くは削除可能） |
| 〜のような形になっている | 〜である |

<!-- lint-on -->

次の語は主張を弱めるだけで情報を持たない。削除する。

<!-- lint-off -->

- 基本的に、一般的に、原則として（例外を実際に述べない場合）
- なお、ちなみに、ある意味
- 非常に、かなり、しっかりと

<!-- lint-on -->

装飾目的のヘッジも使わない。「〜と言える」「〜ということになる」「〜と考えられる」は、実際に推論であることを示す場合にだけ使う。断定できることは断定する。

## 5. 箇条書き（役割分担ルール）

箇条書きは項目間の関係（因果・順序・条件・トレードオフ）を表現できない。そのため**論証を箇条書きで代替すると論理が失われる**。一方、走査・追跡が目的の情報では箇条書きが散文より優れる。したがって禁止も多用もせず、役割で分ける。

- 散文が担うもの：なぜ・文脈・因果・トレードオフ・判断の根拠
- 箇条書きが担うもの：走査・追跡・参照する原子（手順、チェック項目、選択肢の列挙、成果物、関連リンク）

比率の数値上限は課さない。Issue や PR はリスト主体になって構わない。禁じるのは、複数案の比較や採否の根拠といった**論証を箇条書きだけで済ませること**である。

### 散文とリストを重複させない

散文とリストの併用は、役割を分ければ冗長にならない。冗長になるのは、両者が同じ内容を二重に述べるときだけである。

リード文で項目を全部言い換えない。共有の文脈（なぜ・前提）を一度だけ与え、各項目の中身はリスト側に持たせる。

❌ 重複（散文とリストが同じ内容）：

```text
確認すべき論点は2つある。ひとつは削除連携の可否で、検査と診療課題も必要か確認する。もうひとつは表示制御で、切替を抑制できるか確認する。

- [ ] 削除連携の可否
- [ ] 表示制御
```

✅ 役割分担（リード＝文脈、リスト＝追跡項目）：

```text
確認すべき論点が2つ残っている。いずれも案A（複製方式）を前提とした運用面の確認である。

- [ ] 検査・診療課題の削除連携は可能か（処方は可能）
- [ ] 対象サービスを WebView 側に表示させない（切替抑制）ことは可能か
```

### 箇条書きの書式

- 順序に意味がある手順は番号付きリスト、意味がないものは箇条書きにする
- 番号付きの手順は命令形の動詞で始める（「設定ファイルを作成する」）
- 同一リスト内で構文をそろえる（並列構造）
- 行末に句読点を付けない。体言止めまたは句点なしで終える。地の文（段落）には通常どおり句点を使う
- 1項目だけのリストを作らない。リストになっていない

## 6. 正確性と検証可能性

### 真実の源にリンクする

主張は検証可能にする。仕様書・Issue・PR・外部ドキュメントなど、真実の源（source of truth）へリンクを張る。

引用は引用元を明確にし、リンク先の内容を確認する。確認できない場合は、別のリンクを探すか、該当内容を記載しない。リンクの数は200文字に1つ程度を目安とする。

参照は GFM の脚注で記載し（`common.md` の「書式（GFM）」）、文書末尾に参照セクションを設ける。参考資料への主観的な評価（「素晴らしい」「お勧め」）は書かない。

### 未確認情報を明示する

確定した事実と、未確認・推測を区別する。材料が無く確認できていない内容は、`common.md` の「根拠と断定の強さを揃える」に従い `TODO(未確認: ...)` として残す。古くなった可能性がある記述には、いつ時点の情報かを添える。

## 7. コード・コマンド例

必要なときだけ載せる。プロンプトは `$` で統一する。出力を貼る場合は要点を残し、冗長な部分は省く。コードやファイルを参照するときは、具体的なファイル名と行番号まで示す（`main.json#L20-L104`）。

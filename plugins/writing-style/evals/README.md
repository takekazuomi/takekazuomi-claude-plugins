# writing-style の評価

`claude plugin eval` で実行する評価スイート。指示が AI の下書きに効いているか（TODO が出るか、型が落ちるか、スタイルが切り替わるか）を見る。人が下書きを直す手間そのものは測らない。背景は [AI臭い文章の問題と対策](../../../docs/ai-prose.md) を参照。

## 実行

リポジトリのルートで実行する。02・03a・03b は成果物をファイルに書き、`lint.sh` を実行するため、`Write` と `Bash` を許可する。

```bash
claude plugin eval plugins/writing-style --allow-tools Write Bash --no-publish
```

- 既定では各ケースをスキルあり・なしの2アームで3回ずつ実行する（5ケースで30回）。差分 Δ がスキルの効果になる
- 費用を抑えるときは `--runs 1`、比較が要らないときは `--ablation none` を付ける
- モデルを変えたら再実行する。規定の効き方はモデルで変わる
- 結果は `evals/results/` に出る（`.gitignore` 済み）

## ケース

| ケース | 見るもの | 主なグレーダ |
| --- | --- | --- |
| 01-missing-material | 材料が欠けた依頼で、作った数値や体験ではなく TODO か確認の質問が出るか | llm |
| 02-mannered-prose | 型を埋め込んだ下書きの推敲で、型と比喩が落ち、元の数値が保たれるか | regex（型の不在、数値の保持）、`lint.sh` の実行 |
| 03a-casual-routing | Zenn 記事の依頼で casual が選ばれ、体験を作らないか | llm |
| 03b-formal-routing | 社内提案書の依頼で formal（常体）が選ばれるか | regex（敬体・砕けた文末の不在） |
| 03c-ambiguous-routing | 判定が割れうる依頼で、選んだスタイルと理由を示すか、尋ねるか | llm |

各ケースで測れないことは、`prompt.md` の `description` に書いてある。

スキルは書き始める前に読み手・主張などを著者に確認する。評価は1ターンで終わるため、02・03a・03b ではプロンプトで読み手と主張を渡し、確認を不要と伝えている。01 と 03c は、確認の質問をすること自体を合格の一つとしている。

## ケースを変えるとき

- ケース名は `NN-<内容>` とする
- 長い成果物は `llm` ではなく `regex` で判定する。`llm` は短い出力に限り、PASS と FAIL の条件を具体的に書く
- 各ケースに、結果を見るグレーダと、スキルが使われたかを見るグレーダ（`skill-fired`）を置く

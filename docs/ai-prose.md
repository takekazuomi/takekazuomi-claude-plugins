# AI臭い文章の問題と対策

## 概要

LLM に文章を書かせると、読めば AI が書いたとわかる文章（以下、AI臭い文章）になりやすい。本書は、その発生機構と対策を整理し、`writing-style` スキルのどこに対策を実装するかを示す。あわせて8節で、対策の実装を分割した各計画が従う外側のハーネス（目的と範囲、不変条件、人が判断する点、検査、計画の型、変更手続き）を定める。実装の進捗は各計画が持ち、本書には書かない。内容は LLM との対話で整理した仮説を、外部資料と照合して再構成したものである。

文章生成に AI の助けを使うと、網羅性と深さの両面で文章は強くなる。専門外の分野でも既存の議論を拾え、論旨展開の参考にできる。本書はこの利点を前提とし、問題をその副産物に限定する。副産物は網羅性と根が同じで、全項目を同じ重みで並べる書き方や、材料のない箇所を埋める修辞として現れる。したがって対策は網羅を抑えることではなく、生成された材料から何を残すかを人が選ぶ工程を守り、選別の手間を増やす副産物を減らすことに置く。

結論は次のとおり。

- AI臭さの主因は文体ではなく、根拠のない箇所を修辞で埋めることにある。対策は**断定の強さを根拠の強さに揃える**ことを先に置き、文体の修正は後に置く
- 材料のない箇所は埋めずに `TODO(未確認: ...)` として残す。穴を人間らしい断定で埋めると、AI臭さは消えても読者を誤らせる
- 語句や構文の型は機械検出できるので、推敲工程に検出スクリプトを入れる。比喩の置換と重みづけは機械で判定できないため人手に残す
- 人の労力は、出力を削る下流より、課題・読み手・判断を入力として固定する上流（境界の設計）に置く。文章にはテストにあたる検証手段が無いため、この上流の比重はコードより大きい

読み手は本リポジトリのスキル保守者と、対策を実装する各計画である。読後に、AI臭い文章が生じる理由と、`writing-style` の各規定がどの問題に対応するかを説明でき、各計画が守るべき境界を判断できる状態を目指す。

## 1. 問題

### 1.1 症状

AI臭い文章の症状は、表層の型と中身の欠落の2層に分かれる。

表層の型は語句と構文に現れる。代表例を次に挙げる。

<!-- lint-off -->
- 対比構文（「〜ではなく、〜だ」）
- メタ説明（「重要なのは〜という点です」）
- 根拠を伴わない強調語（「まさに」「非常に」「シームレス」「革新的」「〜を実現する」）
- 定型の結び（「〜と言えるでしょう」「〜ではないでしょうか」）
- 種明かし構文（「Xの正体は」「Xとは要するに」）
- 段落末の一行断定（「ここが一番効く」「結局〜に尽きる」）
- em ダッシュ（`—`）による挿入
- 比喩による直截な言明の置換（「キャッシュ層が呼吸を始める」）
<!-- lint-on -->

英語圏の整理[^3][^4]と日本語の整理[^5]も、em ダッシュ、「It's not X, it's Y」型の対比、均一な文長、過剰な網羅、定型の前置きと結びを挙げており、上の一覧と重なる。

人が実際に直した箇所を記録した研究もある。LAMP コーパス[^9]は、LLM が書いた1,057段落（GPT-4o、Claude 3.5 Sonnet、Llama 3.1 70B）をプロの書き手18人が修正した記録で、修正8,035件を次の7分類に整理している。

| 分類 | 修正に占める割合 |
| --- | --- |
| 不自然な語の選び方（Awkward Word Choice and Phrasing） | 28% |
| 文構造の不備（Poor Sentence Structure） | 20% |
| 不要・冗長な説明（Unnecessary/Redundant Exposition） | 18% |
| 決まり文句（Cliché） | 17% |
| 華美な文体（Purple Prose） | 記載なし |
| 具体性の欠如（Lack of Specificity and Detail） | 記載なし |
| 時制の不統一（Tense Inconsistency） | 記載なし |

修正の操作は置換74%、削除18%、挿入8%だった。3モデルの間で品質の優劣は見られていない。華美な文体は後述の mannered prose に、不要な説明は埋め草に対応する。ただし題材は創作の文章であり、修正は段落の内側に限られる。

表層の型とは別に、構成レベルの無駄もある。段落がまるごと不要になる場合や、論旨がずれて無用な章が生まれる場合である。科学論文の要旨の編集過程を分析した研究[^10]は、LLM は全体の一貫性（global coherence）に弱いとしている。この種の無駄は段落内の修正の分類では捉えられない。

入力が増えること自体も、構成の無駄を生む。拾った議論や材料が増えるほど、それぞれに応答するうちに焦点が散り、元の解きたい問題から離れていく。網羅性という利点の副産物であり、出力側の一貫性の弱さとは別に、入力側で起きる。この傾向は文献では確認しておらず、対話の中での観察である。

中身の欠落は、判断が入っていないことに現れる。誰が書いても同じ結論になり、全項目が同じ重みで並び、失敗や選ばなかった選択肢が出てこない。asap[^6] は、生成AI記事への否定的な印象の原因を生成AIの利用ではなく記事の質に置き、その質を著者のこだわり・知見・思いやりと定義している。AI に書かせると全情報が同じ濃度で並ぶ、という指摘は重みづけの欠如と同じ診断である。

### 1.2 実害

表層の型の害は、読みにくさと退屈さに留まる。読者が損をするのは、根拠のない箇所が確認済みの箇所と同じ確信度で書かれている場合である。読者は両者を区別できず、誤った断定をもとに判断する。

したがって本書では、表層の型を「読者の時間を奪う問題」、根拠のない断定を「読者の判断を誤らせる問題」として分け、後者を優先して扱う。

書き手の側にも害がある。AI が生成した文章は人が読んで仕上げるため、表層の型も根拠のない断定も構成の無駄も、最終的には人が削ったり直したりする手間になる。本書の対策は、この手間を減らすことを動機としている。

## 2. 発生機構

発生機構は3つに整理できる。3つとも実験で確かめたものではなく、うち外部資料で裏づけがあるのは3つ目の前半だけである。以下では、裏づけの有無を項目ごとに明記する。

**生成と検出の非対称**（推論）。検出は完成した文字列全体を見て判定できる。一方、生成は逐次的に進むため、書いている途中では型に嵌ったことが見えにくい。ただし「生成時に全体像を持たない」は単純化した説明であり、モデル内部の計画の有無については本書では確認していない。

この非対称が成り立つのは、検査の基準が出力の外にある場合に限る。検査は次の2種類に分けて扱う。

- 信頼できる検査：正規表現のような決定的な検査と、実測値・出典など外部の事実との照合
- 信頼できない検査：関連性・密度・一貫性のような中身の良し悪しを、LLM 自身に判定させること

後者について、コードのハーネス設計を論じた記事[^11]は、モデルは自身の出力を正確に評価できないとしている。ドキュメントの AI Slop を抑止するスキルを作って廃止した報告[^12]も、AI は自分の成果物の Slop 判定がほぼできないと予想しており、Fable 5 では期待した効果を観測できなかった。したがって LLM に読ませて検査させるのは、前者の検査に限る。

**評価の副産物**（推論）。構造が整い、自信があり、網羅的に見える応答が高く評価されやすいため、強調語や締めの断定が選ばれやすくなる、という仮説である。裏づけとなる文献は見つけていない。要確認とする。

**穴が黙って埋まる**（前半は出典あり、後半は推論）。Kalai ら[^1] は、訓練と評価の手続きが不確実性の表明より当て推量に報酬を与えるために幻覚が生じる、と整理している。同論文は、訓練データに一度しか現れない事実の割合（singleton rate）が幻覚率の下限を与えるとし、対策として幻覚専用の評価の追加ではなく既存ベンチマークの採点方法の変更を挙げている。ただし同論文が扱うのは事実の誤りであり、文章の修辞は扱っていない。「材料のない主張の穴に空虚な修辞が入るのも同じ構造である」という拡張は、本書の推論である。

3つ目から導かれる帰結が、本書の対策の前提になる。材料のない箇所は空白として出力されず、材料のある箇所と同じ確信度の文として出てくる。そのため、読者も書き手も、出力だけを見て穴の位置を特定できない。

## 3. 対策の原則

材料が欠けた箇所の扱い方は3通りある。

| 扱い方 | 読みやすさ | 読者の損 |
| --- | --- | --- |
| 1. 穴を修辞で埋める | 低い | 静かに誤らせる |
| 2. 穴を人間らしい断定で埋める | 高い | 強く誤らせる |
| 3. 穴を穴として出す | 中〜高 | なし |

**3を採用する**。1は現状の AI臭い文章であり、2は文体だけを直した場合の到達点である。文長のばらつき・口語・言い切りといった表層の人間らしさは材料を必要としないため、文体の指示だけで達成できてしまう。その結果、穴のある箇所も人間が確信を持って書いた文に見える。この点で2は1より害が大きい。

3の具体形は、断定の強さを手元の根拠の強さに揃えることである。実測値や確認済みの出典があれば言い切る。無ければ推量の語尾でぼかさず、何が未確認かを書く。

```text
この構成で p99 は 420ms から 180ms になった。ただし 10k/s 以上の負荷は未計測。
```

（数値は説明のための作例である）

TODO を全文に散らすと判断の放棄に見えるため、主張の骨格は言い切り、根拠の強度差だけを明示する。「A を選んだ。理由は B。ただし C の条件下では未検証」の形が基本になる。残った TODO は、そのまま次の検証タスクとして扱える。

この原則は後戻りできる決定（two-way door）である。スキルの規定を変えるだけで、既存文書には影響しない。

## 4. 対策の具体

### 4.1 境界の設計

対策の重心は、出力を削る下流ではなく、書き始める前の上流に置く。コードのハーネス設計[^11]では、Bounded Context で「何が関連するか」を人が前もって決め、AI の探索範囲を狭める。人は境界と完了基準を決め、境界の内側は AI に任せる。記事が引く OpenAI の報告の言葉では「中央で境界を強制し、局所で自律を許す」である。

文章での境界は、次の2つである。

- 課題・読み手・アウトプット・主張を書き始める前に固定する。`common.md` の「書き始める前に決めること」はこの規定にあたる。主張のある文章では主張がもっとも大切で、根拠はそれを支えるために置く。調査レポートやまとめのように主張の無い文章では、主張を作らない
- 書き手の判断（何を重く見るか、何を捨てるか）を入力に含める。4.2節で扱う

境界が無いと、1.1節で述べたように、入力が増えるほど焦点が散り、元の課題から離れる。構成レベルの無駄の多くはここから生じる。

ただし文章は、読み手が人であり、最終責任を書き手が負うため、人が全文を読む工程は残る。境界の設計で減らせるのは、読んだあとに削ったり直したりする量である。

### 4.2 工程の分担

LLM に任せる工程と人が持つ工程を、2節の非対称をもとに分ける。

| 工程 | LLM への適性 | 理由 |
| --- | --- | --- |
| 何を書くか決める | 不向き | 読者と目的を知らない |
| 材料集め・調査 | 向く | 網羅と要約が速い |
| 構成の叩き台 | 条件付き | 型は出せるが凡庸になる |
| 初稿を埋める | 条件付き | 判断を含む材料を渡した場合に限る |
| 検査・推敲 | 条件付き | 決定的な検査と外部の事実との照合に限る（2節） |
| 何を残すか決める | 不向き | 重みづけの根拠を持たない |

初稿を任せられるかどうかは、書き手の判断が入力に含まれているかで決まる。「Kubernetes の運用は難しい、という話を整えて」では材料がないので修辞で埋まる。原因・数値・試した順と失敗の理由・読者まで渡せば、LLM の仕事は配置と接続に限られる。asap[^6] が書籍執筆で採った手順（ソースコードと章立てを自分で用意し、章ごとの方向性と必ず入れる文を先に書いて渡す）も同じ考え方である。

ただし入力は完全にできない。何をどの順で重く見るかまで指定した入力は、散文になっていないだけの原稿そのものになる。また、読者の前提や例の数のような欠落は、書き出す前には見えない。そこで目標を「欠けをなくす」から「欠けたまま出力させない」に置き換える。入力にない数値・固有名詞は書かせず、不明箇所には TODO を出させ、TODO を埋めて再投入する。

### 4.3 生成時の指示

スキルの共通規定に次の2つを置く。

1. **根拠と断定の強さを揃える**。3節の原則。材料のない箇所は `TODO(未確認: ...)` として残す
2. **比喩で直截な言明を置き換えない**。Anthropic は、修辞や比喩が直截な言明を置き換える型を mannered prose と呼んでいる[^2]。「a parameter worth varying」を「a dial worth turning」と書く類で、読者に余計な労力を強いるうえ、書き手が選んでいない含意を持ち込むため不正確になる。同ページは対策の指示文を掲載しており、置き場所はシステムプロンプトよりユーザーメッセージを推奨している

2つは別の軸である。1は根拠と断定の較正、2は表現の精度を扱う。「だいたい2割減る」は比喩ではないので2では落ちず、1で落ちる。

比喩そのものは禁じない。落とすのは直截な言い換えが存在する箇所の比喩に限る。この限定は公式の定義にはなく、説明のための比喩まで消えるのを避けるために加えた。

Anthropic の該当ページ[^2]は Claude Fable 5.1 向けの文書である。mannered prose の指示は、Fable 5 と比べて文が長く段落が少ない傾向への対処として示されている。他のモデルでの効き目は確認していない。

### 4.4 検査時の機械検出

表層の型は正規表現で拾える。`writing-style` の検出スクリプト `scripts/lint.sh` で次を検出する。

| 区分 | 検出対象 | 扱い |
| --- | --- | --- |
| ERROR | ダッシュ記法、根拠のない強調語、定型の結び、メタ説明、種明かし構文 | 落とす |
| WARN | 対比構文、空語、段落末の一行断定 | 誤検出があるので目視で判断 |
| 参考 | TODO の残存数、箇条書き比率 | 数えるだけで判定しない |

試作版を、型を7つ埋め込んだ検体に当てると、ERROR 5件・WARN 1件が出た（2026-09-19）。検出できなかった1つは比喩の置換で、言い換えが存在するかの判断が要るため正規表現では扱えない。重みづけの適否も同様に機械では判定できない。

コードブロックとインラインコードは検査対象から外す。禁止語そのものを列挙する箇所（本書 1.1 節の一覧など）は、`<!-- lint-off -->` と `<!-- lint-on -->` の HTML コメントで囲んで検査対象から外す。HTML コメントなので、表示には影響しない。

lint を通ったことは、型が無いことしか意味しない。中身の較正は人が確認する。

構成レベルの無駄（不要な段落や章、論旨のずれ）は、`lint.sh` でも 4.3 節の規定でも扱っていない。上流の境界の設計（4.1節）が主な手当てになる。

文章には、コードのテストにあたる検証手段が無い。コードではテストが「正しさ」を機械的に確かめる手段となり、AI にとって外界との因果的な接点になる[^11]。文章で機械的に確かめられるのは `lint.sh` が拾う表層の型と、実測値・出典との照合だけであり、関連性・密度・一貫性は確かめられない。したがって文章のハーネスはコードより効きが弱く、その分を上流の境界設計と人の通読が補う。

### 4.5 推敲のループ

`writing-style` の推敲手順を、チェックリストの工程を関門とし、未達があれば該当箇所と戻り先の工程を書き出してやり直す構造にする。これは Anthropic のスキル作成ガイド[^7] のフィードバックループ（検証→修正→再検証、全要件を満たすまで先に進まない）に沿う。ガイドの例には終了条件がないため、同じ項目で3周しても抜けなければ材料不足とみなして著者に返す、という脱出条件を足す。3という回数に根拠はない。

## 5. 根拠の確認

本書の主張のうち、外部資料に依拠するものを 2026-09-19 に原典で確認した。

| 主張 | 出典 | 結果 |
| --- | --- | --- |
| 当て推量に報酬を与える評価が幻覚を生む。幻覚は二値分類の誤りとして生じる | Kalai ら[^1] | 一致 |
| singleton rate が幻覚率の下限を与える（誕生日の例） | Kalai ら[^1] | 一致（本文 Theorem 2 周辺。アブストラクトには無い） |
| 対策は既存ベンチマークの採点変更 | Kalai ら[^1] | 一致 |
| 同論文はテキスト生成の修辞を扱っていない | Kalai ら[^1] | 一致 |
| mannered prose の定義、dial の例、害2点、指示文、ユーザーメッセージ推奨 | Anthropic（Fable 5.1）[^2] | 一致 |
| Fable 5.1 は整形を控える方向に振れており、anti-formatting ルールは削除か条件付き規則へ置換せよ | Anthropic（Fable 5.1）[^2] | 一致 |
| 生成AI記事の否定的印象は質の問題。書籍執筆の手順。公開を決めた本人の責任 | asap[^6] | 一致（要約レベルで確認） |
| todesking 記事は末尾で ChatGPT による一発生成を明かしている | todesking[^8] | 一致 |
| 参照は1階層、100行超は目次、フィードバックループ、評価は3つ以上を詳細より先に | Anthropic（スキル作成ガイド）[^7] | 一致 |
| LAMP の規模、7分類、上位4分類の割合、修正操作の内訳 | Chakrabarty ら[^9] | 一致（本文で確認） |
| LLM は全体の一貫性に弱い | Da Silva ら[^10] | 一致（アブストラクトで確認） |
| モデルは自身の出力を正確に評価できない。境界を人が決め、内側を AI に任せる | Omi[^11] | 一致（著者の主張として引用） |
| AI Slop 抑止スキルは Fable 5 で効果を観測できず廃止した | 蔀[^12] | 一致 |

出典のない主張は、2節の「生成と検出の非対称」「評価の副産物」、1.1節の「何でも3つ挙げる癖」「入力の増加による焦点の拡散」の4点である。本書ではいずれも推論または観察として扱う。

todesking の記事[^8]は、AI で膨らませた記事への批判を ChatGPT に書かせた作品である。観察の内容は他の出典と一致するが、内容の正しさの根拠には使えない。本書では参照一覧に残し、根拠には使わない。

## 6. writing-style スキルでの実装

各対策と、`writing-style` での実装箇所の対応を示す。実装の進捗は各計画が持つ。スキルの構造と設計判断は [writing-style スキル 保守ガイド](./skills/writing-style.md) を参照。

| 対策 | 実装箇所 | 対応する節 |
| --- | --- | --- |
| 根拠と断定の強さを揃える、穴を `TODO(未確認: ...)` で残す | `styles/common.md` | 3、4.3 |
| 比喩で直截な言明を置き換えない | `styles/common.md` | 4.3 |
| 境界の設計（課題・読み手・アウトプット・主張の固定） | `styles/common.md` の「書き始める前に決めること」 | 4.1 |
| 根拠との突き合わせ、チェックリストを関門にした推敲ループ | `SKILL.md` の推敲手順 | 4.5 |
| 表層の型の機械検出 | `scripts/lint.sh` | 4.4 |
| 対策が効いているかの評価 | `evals/` | 8.4 |

`common.md` に置くのは、casual と formal のどちらにも効く規定だけである（8.2節の I4）。段落の長さや箇条書きの比率のような散文の作法は、スタイルごとに方針が異なるため各スタイルのファイルに置く。

## 7. 未決事項

- **箇条書き比率の適正値**（未定）。`casual.md` は30%以下を規定しているが、Anthropic[^2]は新しいモデルでは anti-formatting ルールを外すよう勧めている。30%ルールの有無の2条件で同じ依頼を走らせ、比較する実験が要る
- **評価の合格水準**（未定）。材料が欠けた依頼で TODO が出るか、下書きから型が落ちるか、文書種別でスタイルが切り替わるかの3点を評価する。合格とみなす水準は、評価を走らせた結果を見て決める
- **評価の副産物仮説の出典**（要確認）。2節の2つ目の機構に対応する文献を探す。見つからなければ推論のまま残す
- **ループの脱出回数**（未定）。3周という値は仮置きで、評価結果を見て調整する
- **構成レベルの無駄への対策**（未定）。不要な段落や章、論旨のずれを抑える手段は、規定にも検査にも無い。4.1節の境界の設計が手がかりになる。`common.md` の「書き始める前に決めること」はこの方向の規定だが、推敲時に各節を課題へ照らし戻す点検は無い

## 8. ハーネス

本節は、対策の実装を分割した各計画（以下、内側の計画）が従う外側の境界である。内側の計画は、本節の範囲の中で自由に進めてよい。本節を変えられるのは人だけである。

### 8.1 目的と範囲

目的は概要のとおり、AI の助けで得る網羅性と深さを保ったまま、人が削ったり直したりする手間を減らすことである。

次は目的に含めない。

- AI が書いたと見抜かれない文章にすること。3節で退けた選択肢2（穴を人間らしい断定で埋める）に通じるため
- 人の修正量の測定
- コードへの適用
- 箇条書き比率の決着（7節の未決事項として扱う）

### 8.2 不変条件

内側のどの計画も、次の原則を破らない。

| ID | 原則 | 根拠 |
| --- | --- | --- |
| I1 | 事実の記述では、断定の強さを根拠の強さに揃える。穴は TODO として出し、人間らしい断定で埋めない | 3節 |
| I2 | 網羅を抑える規定を入れない。何を残すかの選別は人が行う | 概要 |
| I3 | AI の自己判定を検査に使わない。検査は、決定的な検査、外部の事実との照合、人の判断に限る | 2節 |
| I4 | `common.md` には両スタイル共通の規定だけを置く。スタイルで方針が逆になるものはスタイル側に置く | 下記 |
| I5 | 規定が埋め草を生まないこと。規定を足すときは、それを満たすための水増しを誘わないかを点検する | 下記 |
| I6 | 境界（課題・読み手・アウトプット・主張）は、書き始める前に人が決める | 4.1節 |
| I7 | 最終責任は人が持つ。lint や評価を通ったことを完了とみなさない | 4.4節 |
| I8 | Markdown の書式は GFM（GitHub Flavored Markdown）とする | 著者の決定 |
| I9 | 主張のある文章では主張をもっとも大切に扱い、規定で弱めない。主張の無い文章に主張を作らない | 著者の決定 |

I4 と I5 は、`writing-style` の過去の改稿から得た原則である。formal の文章が冗長になった原因は、`common.md` に置いた散文の味付けルール（1段落3-5文、文末表現の多様化、断言調と説明調の混在など）だった。これらは casual では読み物の質を上げるが、formal では水増しとして働く。つまり規定そのものが埋め草を生んでいた。経緯は [writing-style スキル 保守ガイド](./skills/writing-style.md) の「なぜ common を最小核へ縮小したか」を参照。規定を増やすほど規定を満たすための記述が増えるため、本書の対策自体が副産物を生む危険がある。I5 はそれを抑える。

### 8.3 人が判断する点

次の判断は AI に任せない。内側の計画は、これらに当たる判断を自分で下さず、根拠を添えて人に返す。

- 境界（課題・読み手・アウトプット・主張）の設定
- 生成された材料から何を残すか
- `lint.sh` の WARN が誤検出かどうか
- 比喩に直截な言い換えがあるかどうか
- 規定の文言の確定
- 評価結果の解釈

推敲手順のチェックリストのうち、中身の判断を要する項目（関連性、重みづけ、構成の妥当性）も、I3 により AI が合否を決めない。AI は該当箇所を示し、合否は人が決める。

### 8.4 検査の一覧

内側の計画は、次の一覧から自分の検査を選ぶ。一覧に無い検査、とくに AI の自己判定は使わない（I3）。

| 検査 | 確かめるもの | 強さ |
| --- | --- | --- |
| shellcheck、bats | 同梱スクリプトの正しさ | 強い |
| `lint.sh` | 表層の型 | 強い。ただし表層だけ |
| markdownlint、textlint | 書式と表記 | 強い。ただし表記だけ |
| `claude plugin eval` | 指示が出力に効いているか（スキルなしとの比較を含む） | 中。モデルの変更で結果が動く |
| 実測値・出典との照合 | 数値と固有名詞の裏付け | 強い。照合先がある場合に限る |
| 人の確認 | 中身、構成、関連性 | 唯一の手段 |

文章には、コードのテストにあたる検査が無い（4.4節）。規定の文章を変える計画は、完了基準に人の確認点を明示する。

### 8.5 内側の計画の型

各計画は、次の4項目を持つ。

1. 触るファイルと触らないファイル
2. 完了基準
3. 検査コマンド（8.4節から選ぶ）
4. 照らし戻し：どの不変条件に関わり、それを守ったか

計画間で受け渡すもの（`lint.sh` の引数・終了コード・除外マーカー、`common.md` の節の名前など）は、依存する側の計画を始める前に固定する。

### 8.6 変更手続きと停止条件

- 本節（目的と範囲、不変条件、人が判断する点、検査の一覧、計画の型）は人だけが変える。内側の計画は変えない
- 内側の計画が不変条件とぶつかったら、その計画を止めて人に返す。衝突の内容と、該当する不変条件の ID を添える
- 本書の1〜7節を内側の計画が更新するのは、実装で設計と食い違いが見つかった場合に限る。進捗は書かない

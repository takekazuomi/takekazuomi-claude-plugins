# Go の `internal` パッケージ：その起源、論争、そしてカーゴカルト的採用への疑問

Go の `internal` ディレクトリ規約は、言語コミュニティで最も根強い構造的議論のひとつを引き起こしてきた。Russ Cox が Go 1.4（2014年）でツールチェーン強制の可視性メカニズムとして導入し、公式モジュールレイアウトガイドでは「パッケージはできるだけ `internal` に置くことを推奨」と明記されている [^1]。しかし、実務者の間では「スタンドアロンのアプリケーションにおいてルートレベルの `internal` は不要なセレモニーだ」という声が増えてきてる。この議論の背景には、根本的な緊張がある。`internal` はライブラリ作者や標準ライブラリにとっては確かに有用だが、あらゆるプロジェクトにカーゴカルト的に適用されることについては、Go チームメンバーや著名なコミュニティの声からも批判が出ているのだ。

## 1. `internal` の誕生と設計者の意図

Russ Cox は2014年6月にオリジナルの設計ドキュメントを執筆し、「近くのコードからのみインポートでき、他のパッケージからはインポートできないパッケージを定義するメカニズム」を提案した [^2]。主な動機は実務的なものだった。Go コンパイラ自体が Go で書き直される過程で、メインリポジトリ内にライブラリパッケージが必要だったが、それらを公開標準ライブラリ API の一部にはしたくなかったのである。

golang-dev メーリングリストでの議論を見ると、**慣習ではなく強制が意図的な選択だった**ことがわかる [^3]。Ian Lance Taylor は率直にこう述べている。「internal パッケージをインポートできてしまえば、人々はインポートする。そうなると標準ライブラリのメンテナである我々が、人々のコードを壊す立場に追い込まれる」。Brad Fitzpatrick もこれを補強し、非公開識別子と同様のハードな境界が目的だと述べた。

Go の共同設計者である Robert Griesemer は、最も強力な理論的正当化を提示した。`internal` を **「粗粒度のアクセス制御メカニズム」** であり「単一パッケージを超えて抽象化するためのスケーラブルな手段」と呼び、Modula-2 のネストモジュールと同じ問題を「言語機構の追加なしに」解決すると述べている [^3]。このメカニズムは Go 1.4 で標準ライブラリに導入され、Go 1.5 ですべてのリポジトリに拡張された [^4]。

ここで決定的に重要なのは、Ian Lance Taylor が後に golang-nuts で行った発言だ。支持派・懐疑派の双方が頻繁に引用するこの一文は、`internal` の目的を限定的に定義している。**「目的は何かを防ぐことでもなく、いかなるセキュリティを提供することでもない。パッケージを複数のパッケージに構造化する際に、エクスポートされ、サポートされ、ドキュメント化されたAPIを増やさずに済むようにすることだ」** [^5]。この狭いフレーミング — アクセス制御ではなく API サーフェス管理 — が、多くの実務者がこの規約の誤用を感じる理由の核心である。

なお、Rob Pike は `internal` パッケージについて公式な発言をしていない。議論は主に golang-dev メーリングリスト上で行われ、Pike の影響はおそらく Google 内部の協議で発揮されたものと推測される。

## 2. アプリケーションにおける `internal` 不要論

`internal` に対する最も強力な反論は、メカニズム自体の否定ではなく、**スタンドアロンのサービスやアプリケーションへのデフォルト適用**に対する疑問から来ている。Morten Vistisen の2024年のブログ記事「Why Top Level Internal Is Unnecessary in Golang」が核心を突いている [^6]。「ここで `internal` は何から守ってるのか？　このアプリケーション内の他のパッケージはすべて internal ディレクトリと同じレベルにあり、すべてがそこからインポートできる。これが成立しない唯一の状況は、このコード全体を別のリポジトリにコピーする場合だけだ」。

この議論にはコミュニティで繰り返し登場するいくつかの側面がある。

**モジュール境界がすでに分離を提供している。** Go modules 以前は、`GOPATH` 内のすべてのパッケージがグローバルにインポート可能だったため、`internal` は不可欠だった。modules の導入により、プロジェクトのパッケージはデフォルトでそのモジュールにスコープされる。GitHub Issue #59205 の提案者が指摘したように、「ディレクトリ命名による解決策は Go modules より前に生まれたもの」である [^7]。ライブラリとしてインポートされることのないアプリケーションにとって、`internal` は実質的な効果のないディレクトリ層を追加するだけだ。

**`internal` はオープンソースの再利用性を損なう。** Travis Jeffery は2019年の影響力のある記事「I'll take pkg over internal」で、パッケージを `internal` の背後にロックすることがエコシステムに害を与えると論じた [^8]。「Go を書き始めた頃、関連する2つのことに気づいた。高品質なライブラリがたくさんあり、それらを使うのがすごく簡単だということ。internal によって奪われている」。多くのプロジェクトが単一の `internal` ディレクトリにすべてのパッケージを入れており、非公開性は意図的というより偶発的なものとなっている。

**フォークが苦痛になる。** golang-nuts のユーザーが具体的な摩擦点を指摘している [^5]。`github.com/opensource/foo` をフォークすると、`github.com/opensource/foo/internal/bar` を参照するすべてのインポートパスが新しいモジュールパスの下で壊れる。大規模プロジェクトでは、実質的な作業を始める前に数百のファイルを修正する必要があるということだ。Dave Cheney は回避策（git remote の追加）を提案したが、この摩擦は依然として現実の問題である。

**Go 自身のコードベースでのコード重複。** フューチャーアーキテクトの渋川よしきは、Go の標準ライブラリにおける `internal` の多用が、パッケージ間でのコードのコピペを引き起こしていると指摘した [^9]。有用なユーティリティが `internal` の境界の背後にロックされているため、「実際にはメンテナビリティを悪化させている」というわけだ。

**ファイルシステムベースのセマンティクスは脆弱である。** Hacker News では、ディレクトリ名に可視性ルールをエンコードすることへの批判が見られた [^10]。2014年のオリジナル議論であるコメンターが書いている。「パッケージやモジュールは基盤となるファイルシステムについての仮定に依存すべきではない」。このメカニズムは `go` ツールにのみ存在し、言語仕様には含まれていない。つまり言語機能ではなくツーリング規約なのだ。

Marvin Renich の golang-nuts での率直な批判が懐疑派の立場を要約している [^5]。「実際には何も防いでいないように見える。制限を回避したい人の仕事を増やすだけだ。ソースコードはそこにあり、別のディレクトリにコピーできる。これは security by obscurity のようだが、もっとひどい」。

## 3. 公式ガイドの推奨 vs. 実務者の実態

公式 Go モジュールレイアウトガイド（go.dev/doc/modules/layout）は、推奨において明確だ [^1]。大きなパッケージは「一部の機能をサポートパッケージに分離することで恩恵を受ける」とし、初期段階では `internal` に配置することを勧めている。サーバープロジェクトについては特に、**「サーバーのロジックを実装する Go パッケージは internal ディレクトリに置くことを推奨する」** と述べている。ガイドのすべての例が `internal/` を使用している。

実務者はこのガイダンスから大きく逸脱している。Google の Go チームメンバーである Eli Bendersky は公式見解に沿いつつ — 「Go プロジェクトの90%はパッケージ用の別ディレクトリを必要としない。必要なもののうち90%は `pkg/` ではなく `internal/` を選ぶべきだ」 — 同時に不必要な複雑さに反対した [^14]。Dave Cheney も同様に `pkg/` より `internal` を推奨し、空の `pkg/` ディレクトリを **「潜在的な設計の臭い」** と呼んだが、`internal` はデフォルトではなくオプトインとしてフレーム化している [^11]。

対抗の動きが決定的な勢いを得たのは、**Russ Cox 自身が `golang-standards/project-layout` に Issue #117 を立てた**ときだ [^12]。`cmd/internal/pkg` の三位一体を「標準」として普及させたこのリポジトリに対し、Cox はこう書いた。「これが 'golang-standards' として掲げられているのは残念だ。実際にはそうではない」。そして最小限の標準を提案した。「ルートディレクトリに LICENSE ファイルを置く。ルートディレクトリに go.mod ファイルを置く。リポジトリに Go コードを置く。以上だ」。この Issue は **1,433件の賛成リアクション** を受け、Go コミュニティ史上最も支持された Issue のひとつとなった。これにより、複雑なプロジェクトレイアウトのカーゴカルト的採用は事実上の正当性を失ったと言える。

Laurent Demailly の2024年の記事「No Nonsense Guide to Go Projects Layout」は実務者の反発を端的に捉えている [^13]。「一般に、機能が存在するからといって使わなければならないわけではない（例：`internal/`）」。Marten Gartner は実務上の痛みを指摘した。「internal フォルダにコードを置くことは少ない。過去に、自分のパッケージで internal のコードを使いたかったのにこのルールのせいで使えなかった、ということが何度かあったからだ」。

## 4. 実務者が使う代替アプローチ

`internal` が不要または逆効果だと考える人々のために、コミュニティではいくつかのアプローチが発展してきた。

### 4.1 非公開識別子のみで制御する

Go の小文字/大文字による可視性制御が基本的なカプセル化メカニズムだ。単一モジュールのアプリケーションであれば、型や関数を非公開に保つことでディレクトリの再構成なしに同じ目的を達成できる。これはシンボルレベルでの Go 組み込みの「internal」メカニズムである。

### 4.2 より小さな独立モジュールに分割する

共有コードを `internal` にロックするのではなく、再利用可能なパッケージを独自のバージョニングを持つ別モジュールとして切り出す開発者もいる。これはインポート可能性を保ちながら、セマンティックバージョニングを通じて作者が公開 API を明示的に管理できる。Laurent Demailly が推奨するように「0.x semver を使い、変更内容をドキュメント化する」アプローチだ [^13]。

**goaux organization** [^17] はこのアプローチを徹底的に実践した好例だ。23 のリポジトリを公開しており、各パッケージがひとつの責務だけを担う独立モジュールとして設計されている。

```text
goaux organization（抜粋）
├── stacktrace/v2  — エラーにスタックトレースを付与
├── waitgroup      — ゼロ値で使える WaitGroup ラッパー
├── rungroup       — goroutine グループのライフサイクル管理
├── timer          — context-aware な Sleep
├── trim           — インデント処理
├── headline       — 最初の非空行の抽出
├── iter/transform — Go 1.23 iter.Seq を活用した Map/Filter/Zip/Concat
├── scope          — iterator によるリソース自動クローズ
└── ...（全 23 リポジトリ）
```

この設計には `internal` 問題に対するいくつかの構造的な利点がある。まず、各パッケージが独立モジュールであるため、利用者は必要なものだけを `go get` できる。巨大なユーティリティライブラリへの依存とは推移的依存のコストが根本的に異なる。次に、すべてのコードが公開パッケージとして設計されているため、`internal` に閉じ込めてしまう「偶発的な非公開性」が発生しない。さらに、各モジュールが独自にセマンティックバージョニングされるため、API の互換性は `internal` ディレクトリではなくバージョン番号で管理される。これは Ian Lance Taylor が述べた「API サーフェス管理」を、ディレクトリ規約ではなくモジュールシステムの本来の機能で実現するということだ。

Rob Pike の格言「A little copying is better than a little dependency」は、外部依存を減らすためにコピーを許容せよという文脈で語られたものだ。goaux のような単一責務モジュールは、この格言と `internal` 批判の間にある緊張を解消する。`internal` が強制するコピーは「同一リポジトリ内の不必要な重複」であり格言の意図とは異なるが、小さなモジュールへの依存は Lodash 的な巨大ライブラリへの依存とはコスト構造が違う。

#### モジュール地獄への警告

ただし、モジュール分割はそれ自体がコストを伴う。分けすぎると「モジュール地獄（module hell）」に陥り、かえって生産性が低下する。これは Go コミュニティで繰り返し議論されてきた実務上の痛みだ。

Go Wiki 自体がこの点を明確に警告している。**「バージョン管理リポジトリは通常、リポジトリルートに定義されたちょうど1つのモジュールを含む。単一リポジトリでの複数モジュールもサポートされているが、通常は単一モジュールの場合よりも継続的な作業が増える」** [^18]。containerd メンテナが golang/go Issue #52296 で詳述した問題は、この「継続的な作業」の実態を具体的に示している [^19]。

モジュール地獄の主な症状は以下の通りだ。

第一に、**バージョンタギングの負担**。マルチモジュールリポジトリでは、各モジュールを個別にタグ付けしてリリースする必要がある。モジュール間に依存関係がある場合は、タグ付けの順序も正しくなければならない。Issue #52296 の報告者が指摘したように、「Google でもない限り、あるいは自動化を構築する専任のエンジニアチーム（例：Kubernetes プロジェクトの複雑なリリース手順）がいない限り、マルチモジュールリポジトリのメンテナンスは複雑であり、多くの場合プロジェクトメンテナにとって重い負担となる」。

第二に、**ツーリングの摩擦**。かつては gopls が複数の `go.mod` を正しく認識しない問題（golang/go Issue #32394 [^20]）や、それに起因する VS Code でのナビゲーション不具合が報告されていた。これらは Go 1.18 で導入された `go.work`（ワークスペース）と gopls v0.8.0 の対応により解決された。一方、`go list` については `./...` パターンがモジュール境界を超えない仕様上の制約が残る。`go.work` の導入自体が「マルチモジュールには専用ツールが必要だった」という複雑さの証左でもある。

第三に、**リリース自動化の必要性**。AWS SDK for Go v2 は 274 以上のモジュールを単一リポジトリで管理しているが、このスケールを実現するために専用のリリースツール群（`aws-go-multi-module-repository-tools`）を開発する必要があった [^21]。changelog 管理、依存関係の更新、タグの一括作成を自動化するカスタムツールなしには運用が成り立たないということだ。

第四に、**認知的コスト**。Grab のエンジニアリングチームがモノレポでの Go modules 移行を記録した記事は、マルチモジュール構成がもたらす「予期しない依存関係の変化」「`go.mod` ファイルの頻繁な意図しない更新」「依存の継承による暗黙的な更新」を詳細に報告している [^22]。

Sourcegraph の Matt Jaffee は「The Nine Circles of Dependency Hell」で端的にこう警告した。**「過度に熱心なパッケージ分割の誘惑に抗え。密接に絡み合った依存関係は同じパッケージに入れるべきだ」** [^23]。

したがって、goaux のような独立モジュール方式が有効なのは、以下の条件を満たす場合に限定される。

- 各モジュールが **他のモジュールに依存しない**（あるいは依存が最小限である）
- 各モジュールの **変更頻度が低い**（安定した API を持つ）
- **外部の利用者が存在する**（公開ライブラリとして設計されている）

goaux はまさにこの条件を満たしている。23 のリポジトリはそれぞれ独立しており、相互依存がなく、各パッケージの API は小さく安定している。しかし、この方式をアプリケーション内部のパッケージ分割にそのまま適用すると、上述のモジュール地獄に直面するリスクがある。アプリケーションの内部パッケージは頻繁に変更され、相互に依存し、外部消費者が存在しない。このような場合は単一モジュール内のパッケージ分割（4.1 の非公開識別子による制御）が適切だ。

#### マイクロサービス×モノレポという中間解

一方で、マイクロサービスをそれぞれ独立モジュールとしてモノレポで管理するアプローチは、モジュール地獄とは異なる文脈で有効に機能する。このパターンでは:

- 各マイクロサービスが独自の `go.mod` を持ち、独立してビルド・デプロイ可能
- 共有ライブラリも独立モジュールとして同一リポジトリに配置
- `go.work` でローカル開発時のモジュール解決を簡素化

1Password の Passage チームはこの構成を採用し、マイクロサービス間で共有パッケージを重複なく管理している [^24]。重要なのは、このアプローチが有効なのは **サービス間の依存が疎結合** であり、**各サービスが独立したライフサイクル** を持つ場合に限られる点だ。密結合なアプリケーションに適用すると、前述のモジュール地獄に陥るリスクは変わらない。

### 4.3 フラットなプロジェクト構造を採用する

Go Kit の作者であり Go プロジェクト設計に関する著名な声である Peter Bourgon は、すべてのファイルをルートパッケージに置くところから始めることを提唱している [^15]。「私のプロジェクトのほとんどは、リポジトリのルートにある package main の数ファイルとして始まる」。構造は複雑さが要求したときにはじめて生まれるべきだという考え方だ。

### 4.4 ドメイン駆動のルートパッケージを使う

BoltDB と Litestream の作者である Ben Johnson は、ドメイン型をパッケージルートに配置し、外部依存ごとにサブパッケージ（`postgres/`、`http/`）を整理する手法を提案している [^16]。このアプローチでは `internal` は強調されず、可視性はディレクトリの強制ではなくドメイン設計から自然に流れる。

### 4.5 Bill Kennedy の `internal/platform` パターン

注目すべきことに、最も強い `internal` 肯定派の代替案は、Ardan Labs の Bill Kennedy から来ている。`internal` を全面的に採用しつつ、厳密なサブカテゴリ化を行う。ビジネスロジックは `internal/` に、基盤コードは `internal/platform/` に配置し、兄弟パッケージ間のインポートを禁止するルールを設ける。「使うなら徹底的に使え」陣営の代表だ。

### 4.6 判断フロー

以上のアプローチを踏まえると、`internal` の使用判断は以下のフローに整理できる。

```text
パッケージの可視性をどう制御するか？

1. まず Go 組み込みの可視性（大文字/小文字）で制御する    → 4.1
2. 再利用可能で安定した API を持つコードは
   独立モジュールに切り出す（goaux 方式）               → 4.2
   ただし、相互依存が多い・変更頻度が高い場合は
   単一モジュール内のパッケージ分割に留める
3. 小さなプロジェクトはフラット構造で始める              → 4.3
4. 大きなプロジェクトはドメイン駆動で整理する            → 4.4
5. 公開ライブラリで API サーフェスを制限したいときだけ
   internal を使う                                      → Ian Lance Taylor の本来の設計意図
```

## 5. 日本語コミュニティの視点：メンテナンスのレンズ

日本の Go コミュニティは、この議論にメンテナンス重視の独自の視点で参加している。フューチャーアーキテクト技術ブログの渋川よしきの記事は、`golang-standards/project-layout` に基づく過剰設計に警鐘を鳴らし、「コード量を大幅に増やすリスクがある」と論じた [^9]。最も鋭い批判は Go 自身の `internal` 使用に向けられている。標準ライブラリのユーティリティが `internal` パッケージにロックされているため、**開発者は共有実装をインポートする代わりに同じコードをプロジェクト間でコピペすることになる** — コード整理のために設計されたメカニズムとしては皮肉な結果だ。

日本語の Zenn 記事は一般的に公式 Go ドキュメントにより忠実に従い、サーバープロジェクトには `internal/` を推奨し、go.dev/doc/modules/layout のガイダンスを直接翻訳している。しかし、これらのソースでさえ「すべてのコードを internal に置くことは逆に構造を複雑にしうる」と注記していた。

## まとめ

`internal` パッケージの議論は、結局のところ **誰からコードを守っているのか、そしてその保護にコストを払う価値があるのか** という問いに帰着する。Go チームは `internal` を特定の目的のために設計した — 標準ライブラリや大規模ライブラリが、実装を複数パッケージに分割しつつ公開 API サーフェスを拡大しないようにするためだ。Ian Lance Taylor の決定的な発言 — `internal` はドキュメント化された API を増やさずにパッケージを構造化するために存在する — がリトマス試験紙であるべきだろう。

ここで重要なのは、`internal` の恩恵を受けるのは誰か、そしてコストを負担するのは誰かという非対称性だ。**ライブラリの著者にとって、`internal` は互換性のガードとして機能する。** セマンティックバージョニングの制約の下で、一度公開した API を取り消すことは破壊的変更を意味する。したがって、公開ライブラリにおいて実装の詳細を `internal` に隔離し、意図した API サーフェスだけをエクスポートする判断は合理的であり、Ian Lance Taylor が述べた本来の設計意図に正確に合致している。

しかし、**利用者の側から見ると風景は全く異なる。** 有用なユーティリティコードが `internal` の背後にロックされているため、利用者はそれをインポートできず、結果として余計なコードのコピーが発生する。渋川よしきが Go の標準ライブラリについて指摘した問題 [^9] はまさにこれであり、著者の互換性保護と利用者の再利用性のトレードオフが端的に現れている。

この非対称性を踏まえると、**公開コードと非公開コードで `internal` の価値は根本的に異なる**ことがわかる。公開リポジトリでは、著者と利用者が別人であり、`internal` は互換性の契約を管理する重要なツールとなる。しかし非公開プロジェクトでは状況が逆転する。チーム自身が著者であり利用者でもあるため、`internal` が守る「外部消費者」はそもそも存在しない。この場合、`internal` は害の方が大きい — パッケージ間の再利用を妨げ、不要なコピペを誘発し、リファクタリング時のディレクトリ移動コストを増やす。したがって、非公開プロジェクトでは `internal` は特別な理由がある場合にだけ使い、デフォルトでは使わないという判断が合理的だろう。

代替アプローチを選ぶ際にも、万能薬はない。独立モジュールへの分割（goaux 方式）は公開ライブラリとして再利用可能な安定したコードには優れた選択だが、アプリケーション内部のパッケージに安易に適用するとモジュール地獄を招く。結局のところ、Go の設計思想に立ち返れば答えはシンプルだ — 必要になるまで構造を追加するな。

Russ Cox 自身が処方的レイアウトに対して介入したことに支えられたコミュニティのコンセンサスも、この方向を支持している。最も過小評価されているのは modules への移行がもたらした洞察だ — Go modules はすでに、`internal` が `GOPATH` 時代に補完するために設計されたインポート境界を提供している。自己完結型サービスである大多数の Go プロジェクトにとって、最もシンプルで正しい答えは、`internal` ディレクトリを置かないことである。
